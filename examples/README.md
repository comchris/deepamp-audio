# examples/ — a sample a session can copy, not a fixture a suite reads

1. **What this directory is.** Checked-in example documents for this plugin's batch path: a file a person or an agent can open, read in one screen, and hand to a verb to see what the lane does with it. Nothing here is a test input — no suite reads this directory — and nothing here is audio. A fixture a suite depends on lives under `tests/fixture/`, and this directory is deliberately not that.

2. **The sample it carries today.** `scene_sample_strek_two_speakers.json` is one short exchange from a real multi-voice Star Trek scene this lane has already rendered, trimmed to eight lines and two speakers. Its dialogue text and its two voice names are the ones that scene was run with, so what is on disk is the shape the lane accepts rather than an invented one. It was added at the operator's request of 2026-11-12 (`TODOS.md` part two item 15, verbatim: "We also want to have a sample multi-speaker audio book batch file for a Star Trek scene within the repo that can also be user as a sample for future agents - please add as pre release todo - like the others above") and the card is `CHANGELOG.md` T-873.

3. **How to use it, in the order that costs nothing.** 1) Read the voices: `GET voice_registry` or `audio_voices {what:"list"}` — a name in a sample is not a name this machine has. 2) Read the slot you mean to dispatch to: `POST endpoint_models {fn, id}` — the model is what that engine lists, and this file names none. 3) Ask for the plan before the render: `audio_render {kind:"plan", file:"<path to the sample>"}` or `POST batch_plan`. Name the model you read at step 2 in that call — the batch route carries no default of its own, and a plan or a scene asked without a model is refused with the read it needs. A plan answers what would be sent — the parts, the cast it would build, the line counts, the ceiling arithmetic — and dispatches nothing, so it is the step that shows you the file was understood. 4) Then dispatch it: `audio_render {kind:"scene", file:…}` or `POST dispatch_batch`. A dispatch answers with rows and ids; the audio arrives later.

4. **The shapes the lane accepts, both of them.** `{"scene_config": {…}, "dialogue": [{"name": "…", "text": "…"}, …]}` is the scene shape; `{"batch_config": {…}, "items": [{"output": "…", "name": "…", "text": "…"}, …]}` is the batch shape. `normalizeBatchDoc` takes either unchanged. Every line must name its speaker — `name` or `voice` — and a `[S1]`-style marker at the front of a line is treated as a leftover and removed, because the lane writes the engine's own markers itself, from the cast of the part that line lands in. One line is one un-splittable unit and is capped at 4 000 characters. A file may decide `max_speakers`, `language` and `instructions` for itself; every other key in its front matter is description, not something the lane executes.

5. **What a sample in this repository must not carry.** No model name (model choice is read from the slot's catalog before a request is sent — a workspace rule, not a style preference). No machine name, address or port. No absolute local path, and no `output_dir`: the lane writes what it renders into its own store and the caller does not choose a directory from a checked-in file. No claim to be a test.

6. **What a sample is for, stated plainly.** It answers "what does a multi-voice batch document look like" for a session that has never built one, and it gives that session a document that is known to be accepted. It does not answer which model, which slot or which voice to use — those are read, every time (`AGENTS.md` 5.2, 5.3).
